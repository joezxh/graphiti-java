# Graphiti 测试文档优化总结

## 优化概述

基于 `system-uaa-test.md` 的优秀测试方法论,对 `graphiti-test.md` 进行了结构化优化,重点提升了测试提示词的可执行性和实用性。

## 已优化模块

### 1. 仪表盘 (Dashboard) 测试提示词

**优化前问题**:
- 测试步骤过于笼统,缺乏具体验证点
- 未引用实际源码文件路径
- 问题诊断缺乏对照表
- 缺少 API 端点对照

**优化后特性**:
- ✅ 明确页面路径、源码文件、组件依赖、API 文件
- ✅ 6 个详细测试场景,覆盖:
  1. 页面加载与基础显示 (Stats 卡片、快捷操作、最近图谱)
  2. 统计数据准确性验证 (API 对比、格式验证、实时性)
  3. 快捷操作功能测试 (路由跳转验证)
  4. 最近图谱列表交互 (点击跳转、空状态)
  5. 刷新功能与错误处理 (网络异常模拟)
  6. 响应式布局测试 (3 个断点)
- ✅ 每个场景包含:
  - 详细的执行步骤
  - 明确的预期结果 (✅ 标记)
  - 具体的验证点
- ✅ API 端点对照表 (GET /api/v1/graph/stats, GET /api/v1/graph/list)
- ✅ 问题诊断对照表 (浏览器现象 → 可能原因 → 检查文件 → 修复建议)
- ✅ 关键验证点提醒 (⚠️ 标记)
- ✅ 测试执行要求

**源码引用**:
- `src/views/dashboard/index.vue`
- `@/components/StatsCard/index.vue`
- `@/api/graph.ts`

## 优化方法论 (来自 system-uaa-test.md)

### 1. 测试提示词标准结构

```markdown
**页面路径**: `/xxx`  
**源码文件**: `src/views/xxx/index.vue`  
**API 文件**: `@/api/xxx.ts`
**权限标识**: xxx (如需要)

```prompt
/browser 或 /open-gstack-browser
[简短任务描述]

【前置操作】
1. 登录系统
2. 导航到页面
3. 等待加载完成

---

【测试场景 N：场景名称】
[详细步骤]

预期结果：
✅ 验证点 1
✅ 验证点 2
✅ 验证点 3

---

【API 端点对照】
| 操作 | API 方法 | 路径 | 说明 |

---

【问题诊断】
| 浏览器现象 | 可能原因 | 检查文件 | 修复建议 |

---

【关键验证点】
⚠️ 关键点 1
⚠️ 关键点 2

【测试执行要求】
1. 按顺序执行
2. 截图保存
3. 记录结果
4. 查看错误
5. 验证 API
```
```

### 2. 测试场景设计原则

1. **从基础到高级**: 先验证页面加载,再验证交互功能,最后验证异常处理
2. **正向+反向测试**: 既有正常流程测试,也有边界和异常测试
3. **具体可执行**: 每个步骤都包含具体的操作和验证点
4. **源码可追溯**: 问题诊断直接指向源码文件行号
5. **API 可验证**: 提供完整的 API 端点对照表

### 3. 问题诊断对照表优势

| 浏览器现象 | 可能原因 | 检查文件 | 修复建议 |
|-----------|---------|---------|---------|

这种结构让 AI 测试代理可以:
- 快速定位问题 (浏览器现象)
- 理解根因 (可能原因)
- 找到源码位置 (检查文件)
- 立即修复 (修复建议)
